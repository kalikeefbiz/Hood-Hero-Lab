# Reservoir gameplay wiring

The location adapter uses the seven doors and the houses in `src/strip/cityMap.ts` for stable IDs. It reads the existing location registry for gameplay links and uses the same game state and command validators as the existing game. There is one save format and one save slot.

## Territory and crime

- Lawful shifts raise the lawful economy through a faction-neutral influence effect. Shopping and regular social actions leave faction control scores alone. Personal trust and membership eligibility use their existing rules.
- Street transactions record local demand, aggregate actor/faction sales, revenue, pressure and police exposure. Actual sales by an affiliated actor can build economic presence. Failed sales can incur losses and heat even when faction economy stays unchanged. The existing territorial stabilization rules still decide control. Independent sellers have market activity without their own faction control score.
- Robberies already record heat, local standing loss, witnesses and cooldowns. Named victims and violence can create personal grievances and retaliation under the existing rules. Pawn sales settle property and money without awarding territorial influence.
- A focused systems task is needed for persistent customer acquisition and repeat business, targeted incumbent responses, and the connection from independent operators’ local market share to faction-level competition. Existing competition is district-wide and aggregate. The adapter leaves those formulas intact.
- The legacy engine can interpret the initial `enemies` relation plus recognition as active war. Canon calls for hostility before sustained violent escalation. A separate rivalry-state change can distinguish tension from war across `Danger`, faction AI and access rules once the station incident’s site is settled. The adapter does not author or relocate that incident.
- The remaining canon residents are approved for future content work. The current engine still has provisional contacts such as `contact-blocks`. Their existing IDs and histories remain valid. New hires use `mr-lewis` and the starting market conversation retains `quanny`.

## Controller contract

Import from `src/city/LocationInteractions.ts`. The API is synchronous and can run in a headless simulation. It consumes the current `GameState` snapshot.

1. Use `resolveReservoirLocation(id)` to resolve a place and enumerate its mapped homes. Pass the map’s exact `propertyId` for a door-level home interaction.
2. Call `queryLocation(state, { actorId, locationId, propertyId, peopleHere })`. Each action has an exact serializable `command`, label, quoted cost or proceeds when available, and an `error` if currently unavailable. Valid actions and targets have `error === null`. `targetId` can identify an item, job, person, inventory stack, robbery target, robbery offer, encounter or session depending on the command. Read tower politics from the same query.
3. The host supplies verified co-presence via `peopleHere` for NPC actions and court contacts. Include the NPC actor itself. Ordinary market queries default to Mr. Lewis and Quanny subject to engine availability and story location. Player commands check the player’s saved place. Only the host can verify a precise property door or a non-player actor’s coordinates.
4. Optionally call `validateLocationAction` to check a command. Then submit the same command with `executeLocationAction` against the latest state and presence. Commit the returned snapshot in the host’s normal serialized state-update path and persist it with the existing save system. An error returns the input state untouched. Result metadata reports net AP, days elapsed, actor action day, wallet deltas and IDs for new engine events, inventory exchanges and street transactions. An idempotent command can succeed with `changed === false`. Query results are snapshots and can go stale. Repeatable actions such as purchases represent a new attempt each time.
5. A trapping host submits the queried session ID and cursor when the current beat is due. The adapter never runs a clock. After a robbery start, the host can continue the existing engine session from `activeRobbery` using `robberyInput`, `takeLoot`, `tryDial`, `pauseRobbery` and `leaveRobbery`. Preparation, leads and partner invitations stay with their established people and locations. The engine continues to validate those session and target IDs.
6. NPC support currently covers shopping, supported relationship actions, employment, rest and the existing street transaction. Pawn, lease operations, authored player conversations and robbery career are currently player-oriented. Serialize state updates with the existing day loop so an NPC cannot take the same daily opportunity twice. No NPC scheduler currently calls this adapter.

Verification lives in `src/tests/reservoirLocations.test.ts`. The tests exercise the real save/load and engine commands without a renderer or input controller.
